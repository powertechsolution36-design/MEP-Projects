# MEP Employee App — Database Schema (Design Only)

Database: **MongoDB**. This document designs the collections, fields, indexes, and lifecycle rules for the new, independent backend. It is a design artifact only — no Mongoose models, controllers, routes, migrations, or actual collections are created by this document.

Source of truth: `DOMAIN_MODEL.md` (entity facts extracted from `MEP_PROJECTS_PWA_original`) and `OPEN_DECISIONS.md` (items this document does not resolve). Every field below is tagged **PWA FACT** (the PWA demonstrates this) or **NEW BACKEND DESIGN** (a decision this new system must make, not dictated by the PWA). Where the PWA leaves something genuinely open, this document writes **UNSPECIFIED BY PWA** rather than inventing a rule.

V2 and V3 were not used as reference, schema, or data source for anything below.

---

## Conventions used throughout

- **Authoritative ID (`_id`):** every document's authoritative ID is a MongoDB `ObjectId`, server-generated at insert time. **NEW BACKEND DESIGN** — the PWA's small per-tenant sequential integers are never used as `_id`.
- **`companyId`:** an `ObjectId` reference to the `companies` collection, present on every tenant-scoped document, mirroring the PWA's `co` field. **PWA FACT** (the PWA already scopes every business record to a company) **+ NEW BACKEND DESIGN** (enforced server-side via a query filter on every read/write, not just a client-side convenience as in the PWA).
- **Display/business sequences:** where the PWA relies on a human-facing number (SO number, PSC number), that number is kept as a plain integer field, generated by a concurrency-safe counter (see "Sequences" section) scoped per company. It is never the document's `_id`.
- **Timestamps:** every collection gets `createdAt`/`updatedAt` (Mongoose-style, or manually managed) — **NEW BACKEND DESIGN**; the PWA does not track creation/update timestamps on most records (it tracks specific business dates like `date`, `regDate`, etc., which are preserved separately and documented per collection).
- **Soft delete:** used only where the PWA's own workflow demonstrates that history must survive a "delete" (see each collection's own "Deletion / Immutability" note). Where the PWA does a hard delete (e.g. `delChkList`, `delItem`, `delUser`), this document preserves that as a hard delete — inventing soft-delete everywhere would be a NEW BACKEND DESIGN not asked for, so it is called out explicitly only where it changes PWA behavior (it does not, by default).

### User Reference Migration (name string → durable `userId`)

The PWA stores a person's **display name** (a plain string) in three places instead of a foreign key:
`Project.engs[]`, `ServiceCall.eng`, `InventoryIssue.staff`.

This schema replaces all three with a durable reference:

| PWA field (name string) | New schema field | Type |
|---|---|---|
| `projects.engs[]` | `projects.assignedEngineerIds` | `[ObjectId ref users]` |
| `svcCalls.eng` | `serviceCalls.engineerId` | `ObjectId ref users`, nullable until assigned |
| `invIssues.staff` | `inventoryIssues.staffId` | `ObjectId ref users`, required |

**No V2/V3 data is imported to perform this migration** — this is a forward-looking schema decision for the new system only; there is no existing new-app data to migrate yet. **NEW BACKEND DESIGN.**

## Sequences (concurrency-safe, per-company human-facing counters)

The PWA's front-end counters (`DB.seq.*`, incremented in-memory with `x++`) are not concurrency-safe and are **not** carried forward as the mechanism. Two true business-facing sequences are identified:

1. **Sales Order number** (`salesOrders.orderNumber`, shown as "SO-`<n>`").
2. **Service complaint number** (`serviceCalls.complaintNumber`, shown as "PSC-`<n>`").

No other PWA field is a genuine externally-meaningful sequence — the rest (`DB.seq.enq`, `.proj`, `.pay`, `.contract`, `.chk`, `.invItem/.invCat/.invLoc/.invIssue/.invTxn`, `.company`, `.user`) are purely internal PWA object-array keys with no business meaning of their own and are fully replaced by MongoDB's `_id`.

**Design (NEW BACKEND DESIGN — the PWA gives no guidance on concurrency safety since it has no concurrent writers):** a dedicated `counters` collection, one document per `(companyId, sequenceName)`, incremented via an atomic `findOneAndUpdate` with `$inc` — the standard MongoDB concurrency-safe counter pattern. This guarantees no two Sales Orders (or Service Calls) in the same company ever receive the same display number, even under concurrent requests, which the PWA's single-device `x++` pattern could never guarantee in a real multi-user backend.

```
counters {
  companyId: ObjectId,
  name: "salesOrder" | "serviceCall",
  value: Integer
}
// unique index: { companyId: 1, name: 1 }
```

## Deletion / Immutability Summary

| Category | Collections/fields | Rule |
|---|---|---|
| **Append-only, never edited/removed** | `inventoryTransactions` (entire collection); `enquiries.followUpLog`; `projects.executionUpdates` | Matches the PWA exactly — none of these are ever edited or removed once written. |
