# Document Authority

**Purpose:** this document exists to remove ambiguity about which document controls which question, for anyone (human or a future Claude session) working on the NEW APP engagement. It is new as of the 2026-09-23 documentation-only control-update task and was created because no such document previously existed in `new-app/docs/`.

## Authority hierarchy

- **`STAGED_IMPLEMENTATION_PLAN.md` controls execution sequencing.** It is the authority for what order the remaining verification/production-readiness work happens in, and for the gate each step of that work must pass through (its `EXACT EXECUTION ORDER` section — STEP 0 through STEP 8 — is the canonical statement of this). No other document may be read as re-sequencing that order; a document that appears to imply a different order (e.g. an audit document written before a later stage existed) does not override it.

- **`API_CONTRACT.md` controls the current NEW APP HTTP API contract.** It is the authority for what the implemented API's routes, methods, paths, auth/role/tenant behavior, request/response shapes, error taxonomy, and endpoint count actually are, as of its last verification against source. Its `ENDPOINT COUNTING STANDARD` and `ENDPOINT COUNT RECONCILIATION` sections are the canonical definition and count for "how many endpoints exist" — no other document's endpoint count (a prior audit, a PWA screen count, a narrative estimate) takes precedence over it.

- **The actual route registration in `new-app/backend/src/app.js` and `new-app/backend/src/routes/*.js` remains the implementation source used to verify the endpoint count.** `API_CONTRACT.md` is authoritative for *documenting* the contract, but it is itself verified against source, not the other way around — if `API_CONTRACT.md` and the actual registered routes ever disagree, the registered routes are correct and `API_CONTRACT.md` is out of date and must be corrected, per its own Reconciliation rule (`API_CONTRACT.md` §14: a mismatch means the contract is NOT considered frozen until resolved).

- **PWA audit/decision-lock documents remain the functional behavior source.** `PWA_COVERAGE_AUDIT_*.md` and `*_DECISION_LOCK.md` (and `OPEN_DECISIONS.md` for anything not yet resolved) are the authority for *why* a given business rule exists and what PWA behavior it traces to — they are cross-referenced by `API_CONTRACT.md` and `STAGED_IMPLEMENTATION_PLAN.md` for that reasoning, but they do not themselves define the current HTTP contract or the current execution order; those are `API_CONTRACT.md`'s and `STAGED_IMPLEMENTATION_PLAN.md`'s jobs respectively.

- **No document can override actual route registration when reporting the current implemented endpoint count.** Not `STAGED_IMPLEMENTATION_PLAN.md`, not a PWA audit document, not this document, not a narrative claim in a chat or report — only a fresh read of `src/app.js` + `src/routes/*.js`, reconciled against `API_CONTRACT.md`'s Endpoint Index per its own Reconciliation section, is authoritative for that number.

- **`E2E_WORKFLOW_VERIFICATION_PLAN.md` governs STEP 3 pass sequencing.** It is the authority for the exact pass sequence (3.0 through 3.8), the mandatory pass gate, the mandatory source-evidence standard (PWA + NEW APP), the read-back verification rules, the finding classification list, and the pass result template that all STEP 3 work must use. No STEP 3 pass may deviate from its sequencing or evidence rules without updating that document first.

- **Individual `E2E_PASS_3_*.md` reports (once created) become the evidence reports for their specific pass.** Each is authoritative only for its own pass's findings, using the structure `E2E_WORKFLOW_VERIFICATION_PLAN.md` defines; it does not override that plan document's sequencing or standards.

- **`PWA_MASTER_WORKFLOW_AND_CONNECTION_AUDIT.md` remains the master PWA workflow/connection reference**, cited by `E2E_WORKFLOW_VERIFICATION_PLAN.md` and by every STEP 3 pass for established workflow/connection facts (e.g. the 12 workflows, the 23 `notify()` call sites, the B1/B2 findings) — those facts are re-confirmed, not re-derived from scratch, unless a pass finds a discrepancy.

- **Actual PWA source (`MEP_PROJECTS_PWA/index.html`) remains the functional authority**, and **actual NEW APP source (`new-app/backend/src/`) remains the implementation authority for current code behavior**, for every STEP 3 pass exactly as for STEPs 0–2 above — no audit document, decision lock, or plan document outranks a fresh read of the actual source when they disagree.

- **Evidence in every STEP 3 pass must be traceable to actual source** (file + function/route/field name + line range or a uniquely searchable code anchor) per `E2E_WORKFLOW_VERIFICATION_PLAN.md` §2 — a citation to "the PWA" or a module name alone is not acceptable evidence and does not carry authority in any pass report.

- **`EXECUTION_CONTROL_AND_DEADLINE.md` (added 2026-09-23) is the authority for the Phase A/Phase B verification-vs-fix protocol and the deadline checkpoints.** It governs how a Phase A verification pass's BLOCKED outcome is handled (the fix-task identifier format `FIX-<PASS>-<NUMBER>`, the fix-priority classification P0–P3, and the re-verification rule required before a pass may move from BLOCKED to PASS) and it sets the deadline checkpoints (also appended to `STAGED_IMPLEMENTATION_PLAN.md`) and the `ON TRACK`/`AT RISK`/`BLOCKED`/`DEPLOYED` status model. It does not re-sequence `STAGED_IMPLEMENTATION_PLAN.md`'s STEP 0–8 order or `E2E_WORKFLOW_VERIFICATION_PLAN.md`'s pass sequence (3.0–3.8) — both remain frozen and authoritative for what is verified and in what order, exactly as stated above; `EXECUTION_CONTROL_AND_DEADLINE.md` only governs how each pass's outcome is handled once produced.
