# Open Decisions — New MEP Employee App

Items the original PWA does not sufficiently define. None of these are resolved here — no business rule is invented to fill a gap. Each needs an explicit decision from the business before the relevant implementation phase.

1. **Authentication/session mechanism.** The PWA has no server, so it demonstrates only "username + plaintext password unlocks a role." Token/session lifetime, refresh, multi-device login behavior, and logout-everywhere are UNSPECIFIED BY PWA.
2. **Permission granularity beyond observed role/menu behavior.** The PWA shows role-based menus plus a few assignment-based checks (checklist sign-role, project engineer assignment, service-call engineer assignment). No per-user override, no custom role, no field-level permission was ever demonstrated.
3. **Audit retention policy.** The PWA keeps entity-specific histories (inventory ledger, payment part-payment edits, enquiry follow-up log, project updates) indefinitely, with no expiry/purge behavior shown. Whether the new system needs a *general* audit log (who changed what, when, across all entities) beyond these specific histories is undecided.
4. **Offline write synchronization.** Explicitly out of scope for this step per your instruction (READ CACHE ONLY for now). The PWA's original localStorage-only model has no concept of a network at all, so it offers no evidence for how offline writes, queuing, or replay should behave in a networked multi-device system — this must be designed fresh, not inferred from the old app.
5. **Conflict resolution.** Same root cause as #4 — the original PWA never had two devices touching the same tenant's data at once, so it has no conflict-handling behavior to preserve.
6. **Notification persistence requirements.** No expiry, archiving, or deletion of notifications was observed; whether the new system needs a retention window or an archive/delete action is open.
7. **AMC/warranty amount → Payment treatment.** The PWA's Contract.amount is never observed flowing into the Payment ledger anywhere (no AMC billing/collection screen exists). Whether AMC amounts should generate Payment records (and if so, on what cadence — per visit? per contract term?) is undecided.
8. **Delivery Challan ↔ Inventory integration.** Delivery challans on a Project are a free-text material log, entirely disconnected from InventoryItem/InventoryIssue in the PWA. Whether the new system should link a challan line to a real inventory item/issue (so returnable-material-on-site and warehouse stock reconcile) is undecided.
9. **Database indexing details beyond what is obvious from usage.** Obvious candidates (company/tenant reference on every collection; lookup fields like SO number, PSC number, username) are noted in database/README.md, but a full indexing plan is a schema-phase task, not defined here.
10. **Reporting architecture.** The PWA generates all reports as client-side CSV builds (and one printable HTML report) from in-memory data. Whether the new system needs a dedicated reporting/analytics layer, scheduled reports, or just equivalent on-demand exports is undecided.
11. **External messaging automation.** The PWA's four canned service-call messages are manual: staff preview the text, then send via a WhatsApp deep-link or copy-paste. Whether the new system should automate SMS/WhatsApp/email delivery (rather than keep it a manual, staff-triggered action) is undecided and was flagged in the assessment as something not to invent.
12. **Username uniqueness scope.** Flagged in DOMAIN_MODEL.md under User — verified against source: the Company-screen admin-creation flow checks the new username against all other tenants' users, but the normal Users/Team `saveUser` flow enforces no username-uniqueness check at all. The PWA therefore does not demonstrate a consistent global or per-company username-uniqueness rule. Whether the new system should enforce uniqueness globally or scoped per company is a NEW BACKEND DESIGN DECISION, not resolved here.
13. **Company deletion cascade completeness.** The PWA's "remove company" cascades across users/enquiries/sos/projects/svcCalls/contracts/payments/notifs but was not observed cascading the Inventory collections. Whether that's intentional or an oversight in the original app, and what the new system should do, is undecided.
14. **Protected/non-deletable tenant.** The PWA hard-codes a demo company (id 1) as non-removable. Whether the new system needs an equivalent "protected tenant" concept (vs. relying purely on operational safeguards) is undecided.
15. **SO division change after project creation.** The SO edit form allows changing division after the linked Project already exists, but no PWA logic re-derives the project's stage list or checklist for the new division. Undecided whether the new system should allow this at all, and if so, what should happen to the already-seeded project.
16. **InventoryIssue "Returned" status is currently PWA-unreachable (verified bug, not fixed or preserved by choice).** The PWA's `issStatus()` derives status from `qty - rqty - used` with operator-precedence bugs: the literal condition gating the fully-"Returned" outcome is effectively `Number(x.used) || 0 > 0`, which — due to JS operator precedence — evaluates as `Number(x.used) || (0 > 0)`, i.e. `Number(x.used) || false`. Any nonzero `used` therefore short-circuits to `Number(x.used)` (truthy, so the "Returned"-only branch is skipped), and when `used` is `0`, the expression reduces to `false`. Net effect: the literal `"Returned"` string is never actually produced by the live PWA's derivation logic. The reachable outcomes observed are: `Issued`, `Return Requested`, `Partially Returned`, `Returned/Used`, and `Consumed`. This is recorded here as an explicit, UNRESOLVED open decision — not silently fixed and not silently preserved: (A) bug-for-bug fidelity — keep `'Returned'` in the schema enum as dead/unreachable, matching the PWA exactly; or (B) corrected behavior — change the derivation so a fully-returned issue (returned quantity covers the full issued quantity, nothing used) can reach a genuine `'Returned'` state distinct from `'Returned/Used'`. `InventoryIssue.js`'s `status` enum still lists `'Returned'` unchanged pending this decision; only an explanatory comment was added there. No status-derivation logic exists yet in the new backend (derivation is deferred, per instruction, to the service layer), so nothing was "fixed" or "reproduced" — this item exists purely to ensure the eventual derivation logic is designed with this fact in view rather than assuming `'Returned'` is a normal, reachable state.

78. **[PWA FACT CORRECTION — supersedes/corrects `OPEN_DECISIONS.md` #16, does NOT delete it] `InventoryIssue` status `"Returned"` IS reachable.** Item #16 above (written during an earlier task, before `PWA_COVERAGE_AUDIT_INVENTORY.md` existed) claimed the PWA's `issStatus()` has an operator-precedence bug making the literal `"Returned"` status permanently unreachable by the live PWA. `PWA_COVERAGE_AUDIT_INVENTORY.md` §10/§25 item 9 independently re-verified this — not by re-reading the expression, but by **directly executing** the exact extracted `issStatus()` code in Node — and found the opposite: `"Returned"` **is** reachable.
